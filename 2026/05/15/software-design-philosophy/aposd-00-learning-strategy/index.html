A Philosophy of Software Design 精读计划：从架构判断力到 SDET 框架能力

1. 学习定位

《A Philosophy of Software Design》不应该只被当成一本“教人写代码”的书。对我当前的发展目标来说，它更适合作为一本软件设计判断力训练手册。

我的主要目标不是单纯提升 Python 语法熟练度，而是围绕以下三类能力展开：

优先级 能力目标 说明
Primary 架构设计能力 学会判断模块边界、抽象层次、接口稳定性、复杂度来源
Primary SDET / 自动化框架设计能力 学会设计可维护、可扩展、可调试的测试系统
Primary 存储专家 / SET 路线基础 学会把复杂存储系统拆成可观察、可验证、可自动化的工程对象
Secondary Python 工具代码能力 作为设计思想的落地方式，而不是学习主线
Secondary Hexo / Git 知识库沉淀 作为长期知识资产输出，而不是简单聊天归档

核心定位：

软件设计判断力 → SDET / 自动化框架设计能力 → 存储测试系统抽象能力。

Python 和博客文章是产物，不是主线。

2. 为什么建议读两次

这本书适合精读，而且适合读两次。

第一次阅读的目标不是完全读懂，而是建立概念索引。例如：

  • complexity
  • dependency
  • obscurity
  • deep module
  • shallow module
  • information hiding
  • tactical programming
  • strategic programming
  • design it twice

第一次通常只能理解字面意思。真正的理解往往发生在实际工作之后：当自己写过难维护的脚本、调试过混乱的测试流程、维护过接口不稳定的工具之后，再回头读这些概念，才会理解它们为什么重要。

第二次阅读应该带着实际案例重读，例如：

  • Jenkins 自动化脚本为什么越写越乱；
  • 测试框架为什么新增一个场景要改很多地方；
  • 日志为什么不足以支持 RCA；
  • 存储测试工具为什么调用方需要知道太多底层细节；
  • 自动化状态为什么散落在不同脚本里。

一句话总结：

第一次读，是建立概念地图；第二次读，是带着工程后悔经验回来校准设计判断。

3. 学习方式：中英对照 + 软件设计概念解释

后续学习每一章时，不做逐字翻译，而采用下面的结构：

3.1 English Key Terms

整理关键英文术语，并解释它们在软件设计语境中的含义。

示例：

Term 中文理解 软件设计语境
complexity 复杂度 不是代码多，而是理解和修改成本高
obscurity 晦涩性 重要信息不明显、不容易被发现
dependency 依赖关系 一个地方的变化会牵动其他地方
deep module 深模块 接口简单，但内部吸收了大量复杂度
shallow module 浅模块 接口成本高，但内部提供的价值低

3.2 Chinese Explanation

把概念翻译成可以直接用于工作判断的语言。

例如：

deep module 不是“代码很多的模块”，而是“用简单稳定的接口，把复杂性吸收到模块内部”。

3.3 Design Principle

每章都要抽象出一个设计原则，而不是停留在读书笔记层面。

例如：

好的模块不是把代码分散，而是把复杂度隔离。

3.4 SDET / Automation Mapping

每章都要映射到测试系统和自动化框架中。例如：

  • 测试入口是否稳定；
  • fixture 是否隐藏了环境初始化复杂度；
  • 失败时是否能定位；
  • 日志是否形成证据链；
  • 状态是否集中管理；
  • 新增场景时是否只需要局部修改。

3.5 Storage Testing Mapping

每章都要映射到存储测试场景中。例如：

  • appliance
  • node
  • host
  • BMC
  • iSCSI session
  • volume
  • snapshot
  • replication
  • network path
  • Jenkins job
  • qTest case
  • JIRA ticket
  • lab scheduler

4. 第一版阅读的补丁策略

我买的是第一版，因此后续学习时需要补充三类内容：

  1. 第二版新增或重写的内容；
  2. 与近几年软件工程实践相关的新上下文；
  3. 与我的 SDET / 存储测试 / 自动化框架场景相关的现代工程案例。

重点补充方向包括：

  • 第二版中的新增思想，例如如何判断真正重要的设计问题；
  • general-purpose module 与 over-generalization 的边界；
  • 与 Clean Code 在短函数、注释、抽象方式上的分歧；
  • 平台工程、云原生、可观测性对软件设计的新要求；
  • AI 辅助开发时代，为什么设计判断力更重要。

注意：

AI 可以更快地产生代码，但不能自动保证设计更好。复杂设计只会让 AI 更快地产生更多复杂代码。

因此，这本书在 AI 编程时代仍然有价值，甚至更重要。

5. Python 能力的位置

学习这本书时，需要加强 Python，但 Python 不应该成为主线。

建议比例：

Python 应该作为设计思想的验证工具，重点加强下面这些能力：

优先级 Python 能力 为什么重要
P0 type hints 表达接口契约
P0 dataclass / model 收敛散乱参数，形成清晰数据结构
P0 exception design 区分失败类型，提高可诊断性
P0 logging design 建立 RCA 证据链
P0 CLI / config design 支撑自动化工具和 Skill 运行
P1 context manager 管理 lab / environment / resource 生命周期
P1 Protocol / ABC 定义 adapter 边界，降低耦合
P1 pytest fixture design 设计测试依赖注入和环境初始化
P2 advanced metaclass / descriptor 暂时不作为主线

学习 Python 的方式应该是设计驱动式，而不是语法刷题式。

例如，学习 complexity 后，可以用 Python 练习：

  • 识别一个混乱测试脚本的复杂度来源；
  • 把散乱参数收敛成 TestContext；
  • 把错误类型拆成明确的 exception；
  • 把 print 日志升级为结构化日志；
  • 把流程脚本改造成可测试、可扩展的模块。

8. 风险提醒

8.1 不要把这本书读成代码规范书

它不是告诉我函数必须多少行、注释必须怎么写、类必须怎么拆。

它真正训练的是：

面对复杂系统时，如何判断什么设计会让未来更容易理解、修改和调试。

8.2 不要把精读变成逐字翻译

精读不是逐字翻译，也不是大量摘抄原文。

更好的笔记格式是：

8.3 不要过早框架化

正确路径应该是：

不要一开始就追求“大而全”的自动化框架。

8.4 不要用 Python 技巧掩盖设计问题

很多代码问题不是“不够 Pythonic”，而是：

  • 抽象层错了；
  • 状态散了；
  • 依赖乱了；
  • 错误不可诊断；
  • 接口把复杂度泄漏给调用方。

这些问题不能靠语法技巧解决，只能靠设计判断力解决。
