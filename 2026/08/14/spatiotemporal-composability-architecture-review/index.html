架构师解读：A Programming Paradigm for Spatiotemporal Composability

结论先行

这篇论文提出的不是一个“更好的插件 API”，而是一种面向动态系统的运行时编程范式：

把组件对环境的修改建模为“带逆操作的 Effect”，把组件对环境的需求建模为“可响应的 Coeffect”，再由统一的 Context Runtime 管理组件的加载、卸载、依赖变化、异步执行、失败恢复和热更新。

它最有价值的架构思想是：组件作者只描述局部事实——“我需要什么”“我提供什么”“这一步怎么撤销”；运行时据此组合出整个系统的生命周期行为。

但论文的保证是有边界、有前提的：它只能恢复经过 Context 中介的状态；inverse 的正确性仍由开发者负责；外部消息、支付、网络写入等 emission 不能自动撤回；系统级定理还依赖 Effects 独立、依赖图无环、组件数量有限等条件。

1. 论文要解决什么问题

传统软件组合通常是静态的：

  • 函数调用在代码中固定；
  • 模块依赖在启动或编译时确定；
  • 组件出现问题时，通常重启进程或容器。

但插件平台、Agent Harness、IDE 扩展、低代码平台和长期运行服务越来越需要：

  • 运行时加载组件；
  • 卸载单个组件而不重启整个进程；
  • 替换某个依赖提供者；
  • 热更新代码；
  • 在依赖缺失时暂停组件；
  • 在依赖恢复后自动重新激活。

论文把这些问题拆成两个正交维度：

维度 核心问题 论文机制
Temporal composability，时间组合性 组件离开时，怎样完整撤销它过去留下的东西？ Revertible Effects
Spatial composability，空间组合性 组件依赖谁？依赖出现、消失或替换时怎么办？ Reactive Coeffects

这里的“空间”不是地理空间，而是组件在依赖拓扑中的位置；“时间”则是组件从加载到卸载整个生命周期上的影响。

2. 架构全景

论文的整体架构可以压缩为：

Declarative Configuration / HMR 声明式配置与热更新入口
↓
Loader / Reconciler 计算组件的增加、退休与替换
↓
Fiber Registry + Lifecycle Runtime target view · committed view · accumulator
↓
Unified Context 统一管理环境交互
同时管理
Revertible Effects action + inverse LIFO accumulator
Reactive Coeffects inject / provide notify / resolve
↓
Managed Environment Files · routes · timers · services · tools · connections

从架构分层看：

  1. Context 是所有受管理环境交互的入口。
  2. Component 是静态定义。
  3. Fiber 是 Component 的一次运行时实例。
  4. Fiber Registry 保存所有实例及其生命周期状态。
  5. Loader 把声明式配置协调为 Fiber 的增加、退休和替换。
  6. HMR 在此基础上完成模块级替换。

3. Revertible Effects：让副作用可撤销

3.1 普通 Effect 为什么不够

传统副作用可以视为对整个可观察环境的一次状态转换，但这种表示只描述“发生了变化”，没有携带如何撤销本次变化的信息。

  • γ（gamma）：执行前状态；
  • δ（delta）：执行后状态；
  • g：本次执行产生的 inverse；
  • Definition 8 首先要求 inverse 将本次执行后的状态恢复为执行前状态。

论文在后续引入观察等价后，才把严格相等放宽为“外部观察者无法区分”，而不要求物理状态逐字节相同。

3.3 为什么还需要 Effect Independence

LIFO 只能解决单个组件内部的顺序。现实系统可能交错执行：

如果此时卸载 A，A 的 inverse 会在 B 已经修改过的状态上执行。

因此论文要求不同组件的 Effects 具有 independence，核心包括：

  1. A 的前向操作、逆操作与 B 的前向操作、逆操作彼此可交换；
  2. B 的操作不会改变 A 在某个状态下生成什么 inverse，反之亦然。

例如，两个组件分别在不同 key 下注册路由，通常可以交换；两个组件修改同一条有顺序的 middleware chain，通常不能交换。

论文给出的处理原则非常重要：

可交换的部分交给 Effects；不可交换的部分必须通过 Coeffects 显式建立顺序。

4. Reactive Coeffects：让依赖能够响应变化

4.1 Coeffect 不只是另一个 DI 名字

论文把依赖环境定义成一个带类型的有限映射：

意思是：

  • 每个依赖由 key 标识；
  • 每个 key 对应特定类型；
  • 当前环境中可能存在，也可能不存在。

组件声明一个依赖集合 d。只有当 d 中的所有 key 都存在时，组件才允许激活。

这和普通 DI 的区别是：

  • 普通 DI 通常在初始化时解析一次；
  • Reactive Coeffect 在每次 Context 变化时重新判断；
  • provider 消失时，consumer 自动退出；
  • provider 被另一个实例替换时，consumer 自动 reload；
  • provider 恢复时，consumer 自动重新激活。

变化被分为：

  • activating：之前不满足，现在满足；
  • deactivating：之前满足，现在不满足；
  • neutral：满足状态没有改变。

运行时不仅记录“db 存在”，而是记录：

这样即使新旧 provider 提供相等的值，只要 provider 的 Fiber UID 不同，runtime 仍能发现依赖被替换并触发 reload。

这是一个重要的架构决策：依赖一致性基于 provider identity，而不是容易误判的 value equality。

4.3 Committed View 为什么关键

假设：

DatabaseProvider 即将卸载时：

  1. 它先进入 Unloading，停止对新组件“提供 db”。
  2. ReportPlugin 的 target view 变成不满足，于是开始卸载。
  3. 但 ReportPlugin 的 committed view 仍保留旧 db。
  4. 因此 ReportPlugin 在 teardown 中还能归还连接、关闭事务。
  5. DatabaseProvider 等待所有依赖者卸载完成。
  6. 最后才真正释放连接池。

所以论文保证的不只是“consumer 先关、provider 后关”，而是：

Consumer 在自己的整个 teardown 期间，仍能读取它激活时绑定的那个 provider。

这解决了很多普通 DI 框架没有处理好的异步销毁问题。

4.4 Isolation 与 Interception

论文还扩展了两种机制。

Isolation 允许同一个逻辑 key 在不同 Context 中解析到不同 realm：

它适合多租户、测试隔离、插件沙箱和不同子树使用不同实现。

Interception 不改变“依赖解析到谁”，而是改变“怎样访问它”。例如给 filesystem Coeffect 附加：

provider 在每次调用时检查这些 metadata。它适合权限、tracing、quota、tenant 信息和只读数据库访问。

由于 interception 不改变 provider identity，修改策略不一定需要 reload consumer。

6. Fiber 生命周期状态机

简单模型只有：

现实实现扩展为：

四个状态的语义是：

  • Inactive：没有安装 Effects；
  • Reloading：正在逐步执行 Effect iterator；
  • Active：Effects 全部安装，依赖解析已提交；
  • Unloading：停止提供服务，等待 dependents，然后执行 accumulator。

6.1 为什么需要 Reloading

组件激活可能包含多个步骤、异步操作，也可能在中途遇到依赖替换或执行失败。

运行时在每个 iteration boundary 检查 target 是否仍等于 committed target。如果已经变化：

  • 停止继续安装；
  • 将目前已经完成步骤的 inverse 组合起来；
  • 转入 Unloading；
  • 撤销已完成的部分。

6.2 为什么异步操作不能简单取消

论文采用 inertia：

一个已经发出的异步 iteration 可以落地，但落地后若发现 target 已变化，就必须立刻进入卸载。

这是现实主义设计。很多 I/O 操作不能安全取消，或者取消本身存在竞态。

因此它不强求“异步结果绝不落地”，而是保证：

  • 过期结果不会使 Fiber 成为 Active；
  • 它造成的 Effect 会被 accumulator 撤销。

6.3 失败如何处理

如果激活中途失败：

  1. Fiber 转入 Unloading；
  2. 回收失败之前已完成的 Effects；
  3. 最终进入带 error 的 Inactive；
  4. 不自动无限重试；
  5. 失败只记录在当前 Fiber，不拖垮兄弟组件。

7. 五组系统级保证

定理 工程含义 关键前提
Preservation Registry 始终结构良好，provider 和 committed view 不悬空 所有状态变化遵守规则
Recovery exactness 卸载 A 后，系统等价于 A 从未参与，但其他组件的变化仍保留 组件 Effects pairwise independent
Ordering / Resolution coherence Consumer 在 provider 后激活、在 provider 前完成卸载；一次 activation 不跨越两个依赖解析版本 committed view、withdrawal guard
Progress 非稳定状态总有生命周期步骤可执行，最终到达 quiescent state 依赖图无环、Fiber 有限、iterator 有界
Confluence 相同外部配置操作，无论内部调度顺序如何，最终稳定状态相同 independence、无失败、provide total、依赖无环

其中最强的是 Confluence：

动态系统经过任意加载、卸载和替换历史后，最终稳定状态等价于“把最终配置从头静态装配一次”的结果。

但必须注意三个限定：

  1. 比较的是最终状态，不是历史输出。
  2. 比较是 observational equivalence，不要求内存地址、分配顺序完全相同。
  3. 失败可能导致不同调度得到不同结果，因此 Confluence 定理排除了失败。

8.1 Effect Tracking

ctx.effect(callback)：

9. 用一个完整例子理解

假设系统有：

ReportPlugin 激活时：

  1. 从 committed view 取得当前 db 和 router；
  2. 注册 /report 路由，获得 unregister inverse；
  3. 创建定时任务，获得 clearTimer inverse；
  4. 注册 reportService，获得 remove-service inverse；
  5. 所有 inverse 组成 accumulator；
  6. Fiber 进入 Active。

现在切换数据库：

  1. 旧 DatabaseProvider 进入 Unloading。
  2. 它立即停止对新 target 提供 db。
  3. ReportPlugin 发现 provider UID 改变，进入 Unloading。
  4. ReportPlugin teardown 期间仍通过 committed view 使用旧 db。
  5. 它依次撤销 reportService、timer 和 route。
  6. ReportPlugin 进入 Inactive。
  7. 旧 DatabaseProvider 此时才允许释放连接池。
  8. 新 DatabaseProvider Active 后，ReportPlugin 以新 provider UID 再次激活。

这里不需要 Loader 手写完整拓扑排序；顺序由 Coeffect 关系动态产生。

10. 从架构师视角看，论文最强的地方

10.1 统一了三个长期分离的问题

通常 cleanup/disposer、DI/service registry、reload state machine 分别存在。论文证明它们其实是一个问题的三个侧面，并将它们放进同一个 Context/Fiber 模型。

10.2 把 Cleanup 从组件级回调细化为原子操作级 Inverse

这是比 deactivate() 更可靠的 locality of concern。开发者组合现有 Effect 时，不必重新编写整个组件的卸载逻辑。

10.3 正确处理异步 Teardown 的依赖顺序

“provider 已停止对外提供，但旧 consumer 仍能在 teardown 中访问它”是很细、也很关键的设计。

10.4 明确区分可交换与顺序敏感行为

论文没有假装所有操作都可交换，而是要求：

  • 可交换操作留在 Effect 层；
  • 顺序敏感关系上升为 Coeffect dependency；
  • 多 provider 场景通过 broker 建模。

10.5 理论与实现映射完整

论文不仅给出抽象代数，还把主要规则映射到 ctx.effect、Fiber state、target/committed、notify、reload/unload、Loader reconciliation 和 HMR。

11. 必须警惕的边界与风险

11.1 “自动恢复”只适用于 Context 内部

如果插件直接调用全局状态、进程事件、文件系统或 socket，却不经过 Context，runtime 就无法追踪。

因此“正确性成为结构性质”必须加限定：

仅对 Context-mediated、带正确 inverse 的 Effects 成立。

在普通 JavaScript/TypeScript 中，组件仍然可以绕过 Context。除非配合 lint、代码审查、受限 runtime 或 sandbox，否则这首先是一种架构纪律。

11.2 Inverse 正确性没有自动验证

Cordis 接受 disposer，但不会证明它满足论文的 inverse 约束。论文在引入观察等价后，用 Definition 37 将 Definition 8 放宽为观察意义下的恢复：

如果 inverse 忘记清理、清理错对象、重复执行不安全、自身抛异常，形式保证就会断裂。

论文建模了 activation failure，但没有完整建模 inverse/disposal 本身失败后的恢复协议。

11.3 外部 Emission 不可自动撤回

论文区分：

  • acquisition：拿到连接、文件描述符、内存或订阅句柄；
  • emission：发送网络包、写出数据、发邮件、扣款或公开事件。

前者通常可以 inverse，后者一旦被外界观察就不能“当作没发生”。现实系统仍需要 outbox、delayed commit、idempotency key、Saga compensation 和 reconciliation job。

11.4 系统级保证依赖强假设

关键假设包括：

  • shared state 全部被 reify 到 Coeffect key；
  • 组件 Effects pairwise independent；
  • key 的操作满足 commutativity；
  • precedence graph 无环；
  • Fiber 数量有限；
  • iterator 有界；
  • component 对声明的 provision 是 total；
  • Confluence 场景中没有失败。

这些不是运行时自动获得的属性，需要接口设计、静态分析和测试。

11.5 循环依赖不是被解决，而是被拒绝

A 依赖 B、B 又依赖 A，会让双方永远 inactive。论文建议拆成：

理论上可行，但会增加组件数量与配置复杂度。大型系统需要配套的图分析、scaffolding 和命名规范。

11.6 依赖版本兼容仍是开放问题

模型主要按 key identity 绑定，不能自动防止 key collision、provider 接口漂移、行为契约不兼容和多版本共存。

Cordis 当前借助 npm peer dependency，但这依赖语义化版本纪律，不能证明行为兼容。

11.7 安全隔离不是 Context 能独立解决的

Proxy/inject 能做 capability mediation，但恶意代码可以直接访问宿主能力。真正不可信插件仍需 WebAssembly sandbox、独立进程、VM/container 或 capability-safe runtime。

11.8 实证证据还不够强

Koishi 的 4000+ 插件说明该模式具有可用性和生态适应性，但论文也明确承认：

  • 只有一个主要生态；
  • 只有一个宿主语言；
  • 没有对照实验；
  • 没有性能开销数据；
  • 没有开发效率量化；
  • Koishi 当前使用 Cordis v3，而论文描述的是重构后的 v4。

因此它证明了“这种架构可以存在并被采用”，尚未证明“它在各类系统里普遍优于替代方案”。

12. 与常见技术的区别

技术 相同点 关键区别
RAII / try-finally 自动释放资源 主要是词法作用域；论文覆盖长期动态组件生命周期
React useEffect Effect 返回 cleanup Hook 受调用位置和同步接口限制，缺少系统级依赖拓扑
DI Container 声明和注入依赖 通常只在初始化解析，不负责 provider 变化后的异步生命周期
OSGi Declarative Services service 出现/消失驱动组件 cleanup 多为手写 callback，异步 withdrawal 协议较弱
Kubernetes 动态替换、依赖和恢复 粒度是进程/服务；论文目标是同一地址空间内的组件
STM/Transaction 回滚修改 事务边界预先固定，主要针对受控状态，不等于长期组件卸载
Saga compensation 可组合 compensation 只恢复业务等价，不是严格 inverse

13.6 把长期状态放在更高层 Coeffect

论文的 HMR 会撤销旧组件并从干净状态重装。组件自己的进程内状态默认不会保留。

需要跨 reload 保留的状态，应提升为长生命周期依赖，例如 SessionStore、TaskLedger、MemoryService、ConnectionBroker 和 CacheService。

这是一条很实用的状态所有权原则。

14. 架构判断

这篇论文提出的是一个有价值、内部一致、工程感很强的研究方向。它最值得吸收的不是某个具体 TypeScript API，而是三条架构原则：

  1. 每个可撤销的资源获取，都应在发生地点产生 inverse。
  2. 每个跨组件顺序约束，都应表现为显式 dependency，而不是隐藏在 callback 顺序里。
  3. 组件卸载应是一个可观察、可等待、有依赖保护的状态机，而不是一个同步 deactivate() 函数。

但不应把它理解成“任意插件代码都能安全热卸载”。更准确的说法是：

当共享状态被 Context 完整中介、原子 inverse 正确、跨组件 Effects 满足独立性、依赖拓扑满足约束时，Runtime 可以把局部资源管理组合成系统级的可卸载、可重配置和最终一致行为。

这已经是相当强的结论，同时也清楚说明了下一步工程工作的重点：不是先实现 HMR，而是先建立 Effect boundary、dependency discipline、inverse contract 和 failure model。
